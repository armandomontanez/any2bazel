# winget-cli → Bazel: a vetted slice

A Bazel workspace overlay for [winget-cli](https://github.com/microsoft/winget-cli)
(MSBuild, C++17 with C++/WinRT, NuGet and vcpkg dependencies), produced by the
any2bazel parity loop. The narrative is in
[`docs/CASE-winget-cli-migration.md`](../../docs/CASE-winget-cli-migration.md);
the frontend is described in
[`docs/REFERENCE-msbuild.md`](../../docs/REFERENCE-msbuild.md).

**This is a slice, not a migration.** Two of the solution's 41 targets are
built: one static library and one DLL, chosen because between them they need
every kind of external dependency the solution has. The value of the directory
is the five `.bzl` files under `workspace/bazel/`, each of which replaces one way
an MSBuild build reads the machine or its own output tree.

**What it achieves:**

- `AppInstallerSharedLib.lib` (30 translation units) and `winrtact.dll`
  (6 translation units, one of them generated by MIDL) build from a pristine
  `git archive` of the repository. No MSBuild output, NuGet restore or
  `vcpkg_installed` directory exists in that tree.
- `diff.py` reports `CONVERGED errors=0 warnings=0` for both against the
  MSBuild Release|x64 reference, with the other 39 targets excluded by name.
  Seventeen negative controls (take one flag, define, include directory,
  source, link option or library away from the Bazel side, or change its
  compiler version) each break convergence.
- The C++/WinRT platform projection generated by Bazel is byte-identical to the
  one MSBuild generates (1,358 headers).
- `winrtact.dll` from Bazel and from MSBuild have the same exports, subsystem,
  DLL characteristics (Control Flow Guard included) and embedded manifest, and
  both links read the same five Spectre-mitigated runtime libraries. Their
  import tables differ by one API set (`api-ms-win-crt-math`), which the
  reference imports and the Bazel build does not: optimization flags (`/GL`,
  `/Oi`, `/LTCG`) are build type and are deliberately not mirrored.

## Layout

`workspace/` mirrors the paths these files occupy inside a winget-cli checkout.

| Path | What it is |
|------|-----------|
| `bazelrc.txt` | → `.bazelrc`. Pins the MSVC toolset and Windows SDK to the versions the reference build used, and undoes the defines rules_cc adds to every compile (MSBuild defines none of them). **`BAZEL_VC` is a machine path: set it to your Visual Studio instance** |
| `MODULE.bazel` | `rules_cc`; the two NuGet packages as `http_archive` with the SHA-512 NuGet itself recorded; the repository rules below |
| `bazel/windows_sdk.bzl` | `windows_sdk`: one **named** version of the installed Windows SDK. Exposes what a toolchain does not carry — contract `.winmd` files and the SDK tools (`midl`, `rc`, `mt`, …) — by label |
| `bazel/msvc_toolset.bzl` | `msvc_toolset`: optional parts of the pinned MSVC toolset. Today the Spectre-mitigated library directory (`@msvc//:spectre_libs`); fails if the component is not installed instead of linking the unmitigated runtime |
| `bazel/vcpkg.bzl` | `vcpkg_install`: runs the project's own manifest, baseline, overlay triplets and overlay ports into a Bazel repository, and generates one `cc_library` per port from vcpkg's file lists |
| `bazel/cppwinrt.bzl` | `cppwinrt_projection`: `cppwinrt.exe` over the SDK metadata, once, instead of once per project into each intermediate directory |
| `bazel/midl.bzl` | `midl`: an RPC interface definition to header and stubs, as declared outputs instead of files written beside the `.idl` |
| `bazel/nuget/*.BUILD.bazel` | What each NuGet package contributes: WIL is an include directory, CppWinRT is a tool |
| `BUILD.bazel` | `//:winrt_platform`, the shared projection |
| `src/binver/BUILD.bazel` | A shared-items project (`.vcxitems`) as a header library |
| `src/AppInstallerSharedLib/BUILD.bazel` | The static library |
| `src/WinGetServer/BUILD.bazel` | The MIDL step and the sources other projects compile from this directory |
| `src/Xlang/.../UndockedRegFreeWinRT/BUILD.bazel` | `winrtact.dll`: `.def` file, embedded manifest, CFG, Spectre runtime |
| `any2bazel.json` | The reviewed decisions: scope, name and path alignments |

## Reproducing

Needs Windows, Bazel 9.2.0, Visual Studio with MSVC 14.51.36231 (its
Spectre-mitigated libraries and vcpkg components included) and Windows SDK
10.0.26100.0. Other versions work if `bazelrc.txt` and `MODULE.bazel` are changed
to match a reference build made with them.

```bash
git clone https://github.com/microsoft/winget-cli && cd winget-cli
cp -r .../examples/winget-cli/workspace/. . && mv bazelrc.txt .bazelrc   # edit BAZEL_VC
bazel build //src/AppInstallerSharedLib \
    //src/Xlang/UndockedRegFreeWinRT/src/UndockedRegFreeWinRT/UndockedRegFreeWinRT:winrtact.dll
```

To run the parity diff you also need the reference: build the solution with
MSBuild and `-bl`, then

```bash
python3 .../scripts/extract_msbuild.py msbuild.binlog . model.msbuild.json --report msbuild.report.json
bazel aquery 'mnemonic("CppCompile|CppLink|CppArchive", //...)' \
    --features=-compiler_param_file --include_param_files --output=jsonproto > aquery.json
python3 .../scripts/extract_bazel.py aquery.json . model.bazel.json
python3 .../scripts/diff.py model.msbuild.json model.bazel.json any2bazel.json > diff.json
python3 .../scripts/triage.py diff.json
```

Run the Bazel build in a checkout **without** MSBuild outputs, or the result
proves less: a stray `x64\Release\Generated Files` on an include path is exactly
the kind of leak the slice exists to rule out.

## Known gaps

1. **39 targets are not built.** Among them everything that needs a WinRT
   component projection (`midl /winrt`, `mdmerge`, `cppwinrt -component`), the
   resource compiler, the C# projects and both packaging projects.
2. **No test runs under Bazel.** `AppInstallerCLITests` needs five of the
   unbuilt libraries.
3. **vcpkg is built in a repository rule**, from the machine's vcpkg and with the
   compiler vcpkg finds: unsandboxed, not remotely cacheable. The split into
   Bazel-fetched sources and a build action is in the
   [Ladybird case study](../../docs/CASE-ladybird-migration.md) (findings 30–33).
4. **The toolchain is the host's**, pinned by version. Nothing here downloads
   MSVC or the Windows SDK.
5. **Precompiled headers are not used.** rules_cc has no MSVC PCH support; every
   translation unit parses `pch.h` itself.
6. **Post-build steps are not reproduced**: `vcpkg z-applocal` (copies the DLLs
   a binary needs beside it) and the copy of
   `Microsoft.Management.Configuration.winmd` into the DLL's output directory.
   Both are in the report under `steps`.
